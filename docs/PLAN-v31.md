# PLAN-v31 · 眼窝里的笑

**状态：下一轮只读设计，未开始运行时实现、未验收、未发布。** 本计划依据当前 v30 独立本地预研源码及其原尺寸图形成；形成时根会话仍在闭环 v29 第四候选，v30 也尚待正式发布验收。实施前必须先完成这两轮、核对在途任务并冻结最新成功版本；不能把本文件、bfe 候选或本地截图当作 v31 的正式改前基线。

## 这轮要让玩家看见什么

下一轮优先让阿拾和拾光对真实成功有清楚、温暖的回应，再用骨面和衣领的宽明暗帮助读懂它。不是再增加一种走路、跳跃或摇摆动作，也不把更多细线当作一轮大更新。

三个具体时刻：

1. **真实拾到去程票或记忆时，拾光会明显高兴。** 在现有 `emoteTime` 窗口中，健康的、自由飞行的拾光采用可辨认的笑弧眼和更开阔的笑口。现有星点仍保留；新增价值是脸本身能表达“收到了”。抱票、抱种子的位置及手不挪动。
2. **真实解开诗灯后，阿拾会回应这次成功。** 先让掀盖、追看拾光和归位路线保持清楚。合盖后若原 `emoteTime` 仍有剩余，再让阿拾的眼窝和齿列笑起来；已经过期就回到原常态，不在归位后补播一段凭空庆祝。自由状态下的拾光可先回应，归位仍沿用已有释然笑容。
3. **灵光不足时，脸要传达疲倦。** 低垂上睑与成功时的上扬笑弧要有不同轮廓；不用颜色变化承担全部区别。身体 `<20`、拾光 `<25` 的原阈值分别保留，不能为了统一表情而统一成一个新阈值。

**验收优先顺序：实际落脚、握盖和归位路线读得清楚 → 疲劳与注意目标读得清楚 → 成功表情读得清楚 → 骨面和衣料更有体积。** 表情不能遮住操作状态。腾空、落地、承载时不新增摇头、全身弹跳或头部反冲，不抢占 v30 已完成的身体反馈。

最小合格结果是：**320 原尺寸下能区分成功回应、低灵光和中性状态，阿拾整块骨面的体积也更明确。** 衣领是配套项；若只能看见多了几条缝线或高光，应继续修改，不据此宣布本轮完成。

## 最小实施范围

### 1. 成功时的脸先做清楚

阿拾成功表情由“缩短同一椭圆”改为可以识别的笑弧眼形，配合较宽的齿列笑口和轻微上扬的颧面。保留两侧眼窝中心、鼻腔、齿列位置和原外轮廓；不放大整个头、不把骨脸换成人脸，也不新增浮在脸前的表情贴纸。正常眼窝与困倦上睑仍有明确暗腔，瞳光不能被整体提亮冲掉。

拾光只补健康、自由状态中的事件笑眼与笑口。原有探头 O 嘴、低灵光半睑、归位释然笑容和珍珠体积完整保留。抱票/种子时只变脸，不动原物件/手锚点，不扩大光晕，不增加第二组星爆。

即时使用已有 `emoteTime>0`，持续时间仍由原引擎消耗。若需要柔和收尾，仅从剩余 `emoteTime` 的最后不超过 0.24 秒推导回落权重；不新增起始时间、延迟队列、循环笑脸或自己的 RAF。迟到读取、暂停和合盖不会制造新一轮事件。

### 2. 骨质用宽明暗承接表情

给下部骨面增加可读的正面、侧颧面与下颌转折，让骨头看起来有厚度。眼窝内维持深色，局部用内缘反光表现骨边；下颌与衣领之间用一块柔和接触暗部拉开前后。

优先用既有轮廓内部的大面和少量渐变，避免纹理噪点、毛孔、密集裂缝、过亮塑料反光或真实恐怖骨骼细节。主体仍是暖象牙色，场景偏色沿用现有 rim reflection；颧骨阴影不覆盖鼻口，不把整个脸压暗。头盖现有铰链、裂缝、额星及绘制矩阵不在本轮重构范围内。

### 3. 衣领只做必要配套

在既有衣料中整理“骨颌在前、围巾领口居中、衣身与背带在后”的宽明暗层次。优先一个清楚的领口上缘与下侧暗面；衣身保持原渐变、纽扣、口袋和斜背带，必要时降低相互争抢的细线强度。

所有颜色仍来自原 `getOutfitPalette()` / tint，自动季节和已有换装不失效。围巾、邮包继续使用现有 `getTravelerMotion()`；不通过加速抖动来表现材质。若此项在 320 原图没有清楚收益，移到后续，不扩大本轮范围。

## 触发与优先级合同

| 实际状态 | 表情处理 | 不得推导的额外行为 |
|---|---|---|
| 阿拾 energy `<20` | 保留疲倦事实，采用清楚的低上睑与原低灵光口部语义 | 不能提高能量、阻塞动作或改阈值 |
| 拾光 energy `<25` | 原疲倦轮廓/能量弧优先于自由状态的开心；归位仍按已有“疲倦地释然”表现 | 不能用开心盖掉低灵光信息，也不能把两角色阈值合并 |
| opening / peek | 保留原探头、注意和层次；这时手盖操作轮廓优先 | 不添第二次开盖、抬头或扩大灵魂入口 |
| presented soul 的 `pose==='return'` | 使用原归位曲线、缩放、alpha、释然笑容；阿拾看向真实呈现位置 | 不从 `game.soul` 重建归位位置，不使笑脸控制飞行结束 |
| 实际 memory / lamp 使 `emoteTime>0` | 健康自由拾光显示事件笑脸；阿拾在不覆盖关键开盖/归位表情时使用事件笑脸，合盖后只消费真实剩余窗口 | 不从灯总数、存档完成数、重开章节或文件加载推造庆祝；不区分本来没有事件来源字段的“某一盏灯专属表情” |
| 中性、走路、跳跃、落地、承载 | 保留原视线与动作；眼神可随实际目标，材料随原矩阵绘制 | 不加落地震屏、摇头、延长 0.2 秒收势或改脚底/rig |
| 暂停 / 减动 | 读取原冻结时间；减动保留静态语义表情，去掉装饰眨眼/渐变过渡，规则与反馈事实仍存在 | 不用墙钟继续表演，不在恢复时补播；不得因减动改变灵光或奖励 |

眼神目标与情绪应分开计算：身体仍追看真实 `shown`，不能为了笑脸将方向重置。冲突时先保住原疲劳和开盖/归位动作语义，再应用成功表情，最后加装饰眨眼。具体混合不得引入两套脸或重复瞳孔。

## 实现位置与硬边界

最多新增一个小型纯表情/骨面绘制模块，例如 `dream-traveler-face.js`，由主线六章的展示层接入。输入仅包含已有的 mode/chapter、body、真实 presentedSoul、cap phase、energy、emoteTime、传入 render time 和 reducedMotion；返回有限、只读的表情视图。它不拥有状态机，不写 game，也不读本地存储。

`DreamGame.drawSkullFront()` 可在明确的主线六章范围内消费精修绘制，其他模式保留 `super`。现有 [`drawStationCharacter()`](../dist/dream-station-art.js) 已按正确顺序调用下部骨脸、盖沿、盖子和手；不要把新头部再叠在其外。

调用顺序必须尊重现有实际链路：先求角色 rig，再求 `getSoulPresentation(character)`，再绘制头部。**不能在 `getCharacterPresentation()` 中反过来求依赖它的 soul presentation，造成递归或两份不同帧的视图。** 表情读取与浏览器只读观察应消费同一纯规则，绘制器确实使用其结果，不能只让 probe 报告一个未被画出的 smile。

拾光继续通过 `drawRefinedSoul()` 接收引擎传入的 `s`；只在原脸部绘制中消费新增事件表情，`pearlBody`、world/inside 层、scale/alpha、票据/种子手和原能量弧都保持。

硬边界：

- `dream-engine-base.js`、`dream-levels.js`、`dream-festival-levels.js`、`dream-cap-art.js`、剧情/选择/奖励/存档映射保持原字节；纯展示改进放在已有子类和画家模块。
- 保持唯一 cap rig。body/head/cap matrix、`CAP_HINGE`、`CAP_GRIP`、grip/clasp/catch、openingWorld 和实际足底全部沿用；新骨面只在原局部坐标里画。
- 旧 v30 performance、真实 mover dx/dy、暂停、死亡、羽毛恢复、E 反转、低能量拒绝、单局结算和 modal 输入来源守卫均不改。
- 节日/旧生存模式像素隔离；故事模式的换装继续使用原调色板。不给六个章节另建六套脸。
- 不改故事文案/头像/结局，不新增技能、按钮、奖励、提示弹窗、收集物、进度字段或网络资产请求。
