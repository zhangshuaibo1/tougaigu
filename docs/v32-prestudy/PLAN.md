# v32 预研：让对白留在画面的上方

## 当前状态与依据

**独立布局预研，已实现最小 CSS / DOM 改动，尚无改后真实浏览器几何或截图，未升版、未发布。** 基点为 `4c0fbacfbc63e06353d9ab3a20f41cb17bbd7553`，它包含尚未正式发布的 v30 动作与 v31 表情研究，产品标记仍为 29.0.0。正式接续必须先完成 v30、v31 的候选、Pages 与公网闭环，再迁移本轮局部差异。

[原始问题截图](before-greenhouse-root-crossed.png) 来自 v30 未升版预研候选工作流 `40926668988`，原路径 `candidate/1280-greenhouse-root-crossed.png`，1280×800，SHA256 `bb781624a53d5d27c305c5b75f9a54c929735a3192c6407fb6bf76edd60c8a83`。已直接查看原 PNG：温室越过根台后，底部中央的阿拾对白横穿角色的脸和上身。该图只证明这个桌面时刻存在遮挡，不证明手机或所有姿势有同一问题。

旧 `.cap-bubble` 使用 `position:absolute; left:50%; bottom:112px`。手机已有独立 `.stage-reading` 静态流，本轮保留它。

## 已实施的选择

两份游戏入口增加一个没有 role、事件或额外文本的 `.stage-communications` 容器，包住原 `.stage-reading` 与原公告。原对白、头像、目标、HUD 和公告各保持唯一节点，顺序也不变。

容器默认 `display:contents`。仅在 **普通故事界面、视口宽度 ≥900px，且不处于节日、失物检查或月亮活动模式** 时生成两列网格：

- 既有 HUD 占第一行，左右仍距舞台 24px，顶部仍为 15px；高度不固定，沿用原状态内容。
- 对白卡在左侧最大 360px 的列中，从第二行开始，跨右侧的两行。正文仍 12px、头像仍 49px，全文自然换行，无新省略号或行数裁切。
- 目标和附近提示在右侧第二行，公告在右侧第三行；目标与公告按自然高度分行，不取另一个固定 `top` 或中央覆盖位置。对白跨行，可降低左侧对白单独挤压第二行的程度；但跨行元素仍参与 auto 轨道高度分配，不能保证任意长文或大字体永远不影响公告位置。
- 行间距 10px、列间距 24px。视口高度 ≤520px 时仍取原紧凑 HUD 顶部 8px，行间距为 6px。没有新增整块 HUD 背景，只有原对白卡做轻微暖边与深紫渐变整理；去掉指向游戏区的尾角，保持正文对比度。

**899px 及以下，以及节日、失物检查和月亮活动界面沿用原定位。** 失物证据卡原本独立定位在右侧，不在本轮网格中，故明确排除其模式，避免新右栏与该证据卡进入同一阅读区。 这是一条明确、待实测的桌面断点，并非已经修好所有平板宽度。900px 两列是否仍留足高位平台可读区，必须由下一节的实际采样决定。

## 保持的行为

所有 JavaScript、角色、物理、资源、存档与奖励文件逐字节不变。`showCapLines()` 原文本、说话人、头像选择、单段 3800ms / 多段 5800ms 时长、现有隐藏逻辑均保持。原 `role=status`、`aria-live=polite`、`aria-atomic=true`、空头像 alt 与屏幕阅读顺序保留。

容器和对白继续 `pointer-events:none`，既有来信与活动按钮原来的 `pointer-events:auto` 保留。没有新增交互、暂停、聚焦、定时器、RAF、跟随角色位置的逻辑或动画。仅布局改为不平移；现有不透明度过渡及系统/游戏减少动态的 `transition:none` 规则沿用。

没有修改舞台、Canvas、控制按钮的位置、尺寸、transform 规则。≤899px 的新容器不生成定位盒；因此原手机 `.stage-reading` 和公告的包含块设计保持。**以上是源码与 DOM 检查结论，尚未用浏览器测得这些矩形前后相等。**

## 正式集成前的实际验收

1. 在已通过的 v31 上仅应用四文件局部差异，重新读最终样式级联；不要拿本预研的 29.0.0 整份入口覆盖正式新版入口。先完成正式版本与缓存引用统一。
2. 沿用现有原生输入温室路线，在自然触发“叶子探出头了，盖子得给它留点地方。”的越根台时刻读取实际 DOM、角色 rig 投影、Canvas 与控制按钮矩形，并保存原图。验证对白不遮阿拾头、上身、脚与附近落脚点；目标、HUD、公告、操作按钮之间无交叠。
3. 利用真实剧场首次开盖的双段对白检查自然换行。其原正文“脑内剧场开演！请勿从鼻孔入场。”和“纸月亮就位。我兼灯光，不兼打扫。”合计 31 个字符。不要将温室 CAP_SCENES 的双段原稿当作实际最长对话：温室的反馈会被 `getJourneyCapLines()` 单段内容覆盖。需要更多长度例子时，应从真实可触发反馈中选择，不注入生产对白。
4. 检查 1280×800、1024×640、900×640 和 899×640。900 / 899 分界应只有预期阅读排布变化，没有 Canvas、操作区或页面宽度变化；两列长文与原公告并存时按实际高度排开。1280 的一张良好结果不能代替 900 或矮屏结果。若顶区实际挡住关键高位平台，再调整本轮布局，不能以读得完为由忽略场景遮挡。
5. 390×844、320×680 回归原静态阅读流、控制中心命中和完整目标提示；节日界面也确认新容器没有生成布局盒。原手机对白两行视觉限制是继承行为，本轮不改变，也不将其说成全文新改进。
6. 读取真实系统与游戏减少动态模式，确认对白无位移、没有新增过渡；检查原 ARIA 状态节点、文本、原按钮与点击穿透。重用已有 HUD 只读几何探针与现有路线，不添加新的游戏时钟、物理帧循环或输入重试。

Canvas、按钮矩形的前后比较应针对相同视口和相同界面状态；只读观察不得直接写游戏坐标、进度、能量、完成状态或正文。真实图审完成前，不能声称“所有角色姿态完全无遮挡”。
