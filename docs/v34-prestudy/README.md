# v34 预研：窄屏近身抬盖留边

**状态：独立开发、局部真实浏览器与独立源码/绘制复核完成；此预研的产品版本仍为 `33.0.0`，没有发布 v34。** 基础是正式 v33 候选 `1d63072bb9a27690ed14b15d3103c6e8a87fa297`。正式候选与发布由 root 在独立工作树完成，并继承届时最新主分支的文档和验收记录。

## 玩家能看到的变化

390 和 320 窄屏中，阿拾与拾光仍在近处、能够同框时，相机会给真实抬起的骨盖、帽饰和握盖手留出空间。身体、拾光、小猫、平台和整幅背景一起使用最终相机投影，帽子没有缩小、挪动或复制。拾光真正远行时继续使用原来的跟随；活动专用取景继续优先。

`baseline-browser/` 是冻结 v33 候选在两个独立浏览器上下文中，用正常模拟触屏输入获得的原图。390 的旧图可直接看到左缘切掉了帽饰和部分盖子；`final-browser/` 的新原图保留了近身完整盖部。这是分开的真实输入对照，不是同一状态、同一帧的像素 A/B。

## 实现边界

新模块 `dist/dream-cap-framing.js` 只做有限矩阵和包围范围计算。它复用当前 render 原本已经算出的 `character` 与 `presentedSoul`，不再计算骨架或归位曲线。11 种现有帽饰和无帽的保守范围来自原绘制路径；范围包含描边，柔光、飘粒子、牵引线和地面阴影不强制扩大构图。

原 update 的相机 `mix` 仍然执行。新增记录保存自上次绘制以来的起点与各原固定步衰减乘积；render 用当前帧的可行区间约束这些原步的加权目标，在背景、世界变换、裁剪和罗盘之前确定唯一 camera。没有约束时逐位保留原 camera；重复 render 没有新的跟随预算；异常、活动进出和新开局不会借用旧预算。没有绘制后回滚相机的技巧，没有新动画时钟。

参与条件是主线六章、Canvas CSS 宽度不超过 480、有效有限上下文、盖子处于 opening/open/returning、没有活动专用取景，且身体中心已在当前视野内，至少一半主体仍可见。合并身魂轮廓必须能放进原世界范围内的视野；进入和保持保护分别需要 24 / 8 CSS 像素的剩余画面空间。中心真正离屏或世界边缘无解时，不强行拉回身体、不拓宽世界。

**稳定近身的目标是保守轮廓外 8 CSS 像素；浏览器验收要求至少 7.5。** 普通近远转场保留原 `dt × 5.5` 缓动，过渡时可能尚未达到该留边。resize 首个已绘制的新尺寸帧可以统一重新取景；暂停无 resize 完全冻结，暂停 resize 只重新排布，游戏时钟、cap 进度与物理状态不前进。减少动态沿用原立即落定行为。不能把这些不同情况概括成“所有动画帧永远有 8 像素”。

当前 DOM 对白和 HUD 由原 CSS 与文本/进度快照布局，`dream-app.js` 不缓存 camera 的世界投影。原生方向/动作按钮继续按原输入语义工作；活动中的实际触屏方向与固定专用相机已检查。本轮没有新增 Canvas 点击命中机制，也不声称完成了全部可选活动。

## 两个必须分开的失败与修复

### 固定等待误判了仍在收敛的相机

第一次适配验证在 390 回近后固定等待 1 秒，断言读到 camera `21.9128697058`、保守帽界 `6.67284` CSS 像素。此时 cap=open、保护 active、可行上界 `20.4853382068`。错误证据中的下一次真实读取自然前进了 13 个原 `1/60` 步，camera 已为 `20.8943859251`，帽界 `7.61971`。

按原 `(1−5.5/60)^13` 衰减预测后一次 camera，与实测差 `3.55e−15`。因此只把新专项的这一固定 1000ms 观察改为最多 3000ms 等待同一个真实 `>=7.5` 几何条件，记录等待开始/结束的相机、区间、时钟和耗时，没有降低边距或改变游戏速度。原报告、驱动、两张失败原图和数学对照在 `diagnostics/adapter-first-*` 与 `adapter-settling-analysis.json`。

### 旧 18 world 单位内缩阻止了真实近身重入

第二次适配验证确实等满了 3000ms：正常触屏惯性把拾光带到 x≈275，身体 x=105，camera≈94.6168。身体中心仍在视野内约 10.38 world 单位，身魂合并后还有约 110 CSS 像素空间，可行 camera 区间 `[0,20.4853382068]` 非空；但初版要求身体中心距边缘至少 18 world 单位，导致 active 永久为 false。

这是产品问题，不能再延长等待或换观察目标躲开。最终把重入条件改为身体中心在当前视野 `[0, viewWidth]`，左右对称；几何滞回、远行优先、原世界范围和原跟随预算保持。新增正常 far→265 / 275 / 282，以及两侧新 0 边界、旧 18 边界内外回归；两项先在旧判据下失败，改产品后通过。独立审阅另外复现了原 278 边界，并在修复后验证 8 条返回路线均恢复稳定 8 CSS 像素保守留边。第二次原报告/驱动/失败原图在 `diagnostics/adapter-second-*`；分析在 `adapter-reentry-analysis.json`，红绿测试原日志也保留。

更早的新单测曾发现初版错误地把“可移动 camera 区间宽度”当作滞回空间，误拒绝世界左端但实际画面充足的 resize。已改用合并轮廓占用后的剩余画面宽度，并单独保留可行区间非空判断。另两处初始测试夹具分别纠正了反向按键未跨过原刹车速度、以及边界样例的初始 camera；原日志在 diagnostics，没有改旧游戏物理来迎合夹具。

## 证据和正式接入

`source-manifest.json` 记录 260 个受保护源码/资源路径、145 个运行文件及全部8个源码变化。此预研不改 package 版本。`independent/` 收录只读独立复核、旧失败边界、修复后的预算与重入报告，以及原绘制范围与最终源码段相同的证明。两份失败报告对应各自当时的旧字节，未回写成最终成功记录。

`scripts/browser_cap_framing_v34.py` 可由正式 smoke 借用现有 browser 调用，也可独立 CLI 执行。新 hook 位于全部旧路线、v32 对白矩阵和 v33 小旅伴之后；失败仍使整轮失败。当前 33.0.0 预研用显式版本直接运行 helper；正式 root 工作树统一升级34时，原 main workflow 会执行新 hook。没有为了压缩用时删除旧截图、物理或网络门槛。

```sh
python scripts/browser_cap_framing_v34.py --url http://127.0.0.1:9345/ --version 33.0.0 --output /tmp/v34-check
node --test --test-isolation=none --test-reporter=tap tests/*.test.mjs
npm run check
```

`verify-helper-adapter.py` 记录借用浏览器、错误处理与真实执行的测试；其中 `synthetic-contracts/` 明确是 API 夹具，不能当作真实网页执行。旧基线 `baseline-driver-executed.py` 记录当时首轮 helper 接口，之后接口已适配，不将它冒充当前可直接调用的 API。

**未证实范围：** 实体手机、Safari、设备 FPS、全部服饰在浏览器中的全动作组合、全部可选活动、由本局部 helper 单独完成的完整剧情，以及 v34 公网正式版本。正式部署前仍须候选完整流程与部署后的真实 HTTPS 全流程；本预研结果不能替代这些门槛。
